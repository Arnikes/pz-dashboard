# B42 server settings and Workshop mods

PZ Console manages one installation and multiple profiles under `DATA_DIR/Server`.
A profile contains `<name>.ini` and `<name>_SandboxVars.lua`. Drafts, history,
transaction recovery, and Workshop installation state live in `DASHBOARD_DIR`;
preserve that volume when updating the panel.

## Connect the right profile

The panel detects the active profile from the container's `-servername` or
`SERVER_NAME`. You can inspect ambiguous profiles manually, but restart-based
application requires a confirmed active profile.

Configuration writes require a confirmed shared, writable data directory.
The panel compares its mounts, the game's mounts, and any `-cachedir` startup path.
A separate mount over `Server/`, individual mounted files, mismatched volumes,
or read-only data can prevent verification. Use a shared directory.

`PZ_CONFIG_FILE` supplies an explicit INI filename. `PZ_VERSION` supplies an exact
B42 fallback version; detected startup logs take precedence. Restarting invalidates
the prior version context. Mount server files at `/server-files:ro` or set
`SERVER_FILES_DIR` / `WORKSHOP_DIR` to make metadata available. The panel can also
read metadata through `docker exec`; stopped containers may use a labeled cached index.

Settings generated by container environment are marked with their source.
`GENERATE_SETTINGS=true` blocks file application until regeneration is disabled
in the server's Compose definition. The panel does not silently edit environment,
ports, or game administrator credentials.

## Draft, files, startup

Form edits automatically save to a **draft**, not the live game files.
Source edits have a separate save action; switching profiles or editor tabs also
attempts to save. Unsaved input survives a failed request in the current tab.
Retry after reconnecting; secrets are not persisted in browser storage.

Settings and Mods load a configuration snapshot when opened or when the selected
profile changes. Live server updates do not reload sources, forms, or draft metadata.
Unsaved input survives navigation; saving, restoring history, and completing an
explicit configuration operation update the editor once.

The stage bar distinguishes draft preparation, file writes, and startup verification.
Selecting a stage opens a review or focuses an action; it does not itself restart the server.
Use `Ctrl/Cmd+K` to find sections, settings, and load-order entries.

“View changes” shows validation and masked diffs. “Close” keeps the draft;
“Discard changes…” asks for confirmation before reloading the current files from disk
into both Settings and Mods. If there are no draft changes, the review only offers “Close”.
“Write files” requires a stopped server.
“Apply with restart” warns players, stops the server, checks revisions, writes files,
starts the server, and waits for PZ/RCON readiness. The confirmation offers a world
backup: off by default for ordinary settings, on for mod changes and Workshop preparation.
Configuration history is saved regardless of the world-backup choice.

Writes preserve unknown INI keys, comments, line endings, and file ownership/permissions.
When creating a missing Sandbox file, permissions are inherited from its INI partner.
Transactions retain recovery records for both files.

## External edits and conflicts

The browser editor uses its loaded snapshot until reopened. Parallel editing is
not supported: saving a draft replaces a newer draft with the page's snapshot,
and writing/applying files overwrites external file changes. The diff review still
shows external changes, and configuration history retains the actual files present
immediately before writing. Secret placeholders continue to preserve saved secrets.

Reopening a clean draft reads the latest files. A draft with pending changes remains
available until applied or explicitly discarded. API clients retain revision checks
by default; they can request the same overwrite behavior explicitly.

A changed draft revision invalidates earlier validation and confirmation.
Configuration history is scoped to the selected profile; restoring history changes
the draft and still requires a separate application.

After startup, the panel checks the written values, game version, readiness, and fresh
Workshop metadata. PZ may regenerate the standard `ResetID` default comment or an
unedited `ResetID` when the world lacks `z_outfits.bin`; recognized changes are recorded.
A user-edited `ResetID` must remain intact. Other INI values are checked exactly.

PZ can reserialize SandboxVars. Existing values, including `VERSION`, secrets, and
unknown keys, must survive. New mod values must match fresh declarations. Formatting
changes are recorded and the pre-write source remains in history.

## Sandbox settings

The form reads the B42 schema and selected mods' effective
`media/sandbox-options.txt`, including available English/Russian translations.
Disabled or missing mods' values remain in a separate group until explicitly removed.
`VERSION` is managed by the game and cannot be edited in the form.

Lua containing expressions disables the structured form. Source view masks string and
number literals with `__PZ_RAW_LITERAL_…__` markers; retained markers restore their original
values. New expression-based source requires `luac -p`. The Docker image includes this
syntax checker; the panel never executes the submitted Lua.

Initial-world conditions, new-character kits, and vehicle generation do not necessarily
change an existing world. Follow field help and verify gameplay effects in the actual game.

## Workshop packages and individual mods

A Workshop ID identifies a Steam package. `Mods=` contains actual `id=` values
from `mod.info`, prefixed with `\` for B42. One package can contain several ModIDs.
Names, folder names, and list position are not used to guess IDs.

Versioned B42 directories are selected for the detected game version; `common` supplements
a compatible branch. A package with only a future branch or only `common` is not
automatically compatible. See [the B42 mod layout announcement](https://projectzomboid.com/blog/news/2024/08/tidy-up-time/).

Add an item link, ID, or collection. Collections offer searchable candidate selection.
Confirming adds packages to the draft's `WorkshopItems`; it does not select their ModIDs.
Nested collections and items from other games are rejected.

For a package that is not yet downloaded:

1. Prepare a draft and choose “Download packages through server”.
2. The first restart changes only `WorkshopItems`, preserving current `Mods`.
   Other edits stay in the draft.
3. Inspect the downloaded package; choose ModIDs, dependencies, load order, and maps.
4. The second restart applies the complete configuration.

Readiness and fresh B42 metadata confirm installation. The Steam manifest is checked when
available; an unavailable manifest is reported as `manifestVerified:false`.
Each restart rechecks IDs, dependencies, compatibility, and Sandbox declarations.
Existing unchanged mod errors may be warnings for unrelated settings edits;
changing the mod composition requires resolving errors.

The Order tab supports drag/drop, up/down controls, and an explicit destination
position. Display sorting does not change load order. Re-enabling a ModID restores
its remembered position for that profile. Maps and their order are changed explicitly;
adding a map does not rewrite already explored regions.

Modpack export includes packages, selected IDs, order, maps, and retained mod settings.
It excludes ordinary world settings, service `VERSION`, secrets, and Workshop binaries.
Import rechecks packages with Steam, modifies the draft, and still needs validation
and application. Dependency metadata is not a guarantee of Lua compatibility.

## Failed operations and recovery

Before writing, both original files and a transaction journal are saved. Partial
writes roll back. After a process failure, unfinished transactions recover while
the server is stopped; a running server must be stopped before recovery can proceed.
On Linux, file data, permissions, and directory changes are synchronized to disk.
If rollback cannot finish, the journal remains and automatic server startup is blocked.

After a failed startup, the written files remain the current base revision. Restore
the previous configuration into a draft, review it, then apply it separately.
The browser editor can overwrite external edits when applying its restored draft.

“Verify running server” checks an already running profile without changing game files
or restarting it. It requires PZ/RCON readiness, matching revisions and Sandbox values,
and fresh Workshop metadata. The background scheduler retries startup verification
every 20 seconds when readiness or metadata is unavailable, even without an open browser.
INI verification accepts CRLF/LF line-ending serialization alongside the recognized
startup-generated ResetID changes. It still rejects other INI text changes, including
setting values and secrets. Successful verification adopts the disk line endings
in panel metadata and preserves pending draft edits without writing game files.
Revision checks for concurrent edits remain exact.
Cancelling package installation removes its new items/IDs from the draft; apply that
change separately. Downloaded Workshop cache remains available.

## Editor API

All endpoints require an authenticated session; mutations need `X-PZ-Request: 1`.
See [API authentication](operations.md#api).

| Endpoint | Purpose |
| --- | --- |
| `GET /api/server-configs` | Profiles, active profile, version, and setting sources |
| `GET /api/config-draft?file=…` | Masked source, forms, revisions, and draft state; `refresh=1` reloads a clean draft from current files |
| `POST /api/config-draft` | Patch `ini`, `sandbox`, `texts`, or `mods`; discard or rebase |
| `POST /api/config-validate` | Review errors/diffs for a draft revision; optional `prepare:true` |
| `POST /api/config-verify` | Verify files against a confirmed external startup |
| `GET /api/mods?file=…&draft=1` | Draft mod selection; omit `draft` for live files |
| `POST /api/workshop-resolve` | Resolve an `input` item link, ID, or collection |
| `POST /api/action` | `prepare-workshop` or `apply-config` with revision and restart choices |
| `GET /api/config-history?file=…` | Profile history |
| `POST /api/config-history` | Restore `historyId` into the selected draft |
| `POST /api/modpack` | Export or import a `pack` into a draft |

Draft mutations include `file` and `draftRevision`. Rebase also requires the reviewed
`currentRevision`; conflicting/stale state returns HTTP 409. Application accepts
`restart`, `warnSeconds`, and optional boolean `backupBeforeApply`.
The browser passes `overwrite:true` to draft mutation, validation, and application.
Draft mutations also include the complete masked `texts` snapshot so newer edits to
other fields do not leak into the page's save. Overwrite permits stale draft mutations
and external file replacement; validation and application still require the reviewed
draft revision, and operation locks, format validation, transaction recovery, and
startup verification remain enforced.
See [the isolated acceptance procedure](acceptance-b42.md) for real-server checks.
