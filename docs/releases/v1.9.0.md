## Changes since v1.7.0

### Telegram notifications

- Add optional MTProxy delivery for Telegram notifications and connection tests,
  including plain, `dd`, and complete `ee` FakeTLS secrets. Configure the proxy
  in **Maintenance → Notifications** or bootstrap it through the panel environment.
- Identify invalid proxy settings and distinguish connection, bot authorization,
  and message-delivery failures. Keep credentials out of user-visible errors and
  process logs, including errors returned by the direct Bot API.

### Configuration and interface

- Unify operation progress and configuration stages with clearer current and
  completed steps. Improve the Workshop package-to-ModID workflow, draft actions,
  empty states, and recovery feedback.
- Clarify saved and unset secret-field states and align settings, source editors,
  and notification controls across desktop and mobile layouts.
- Make initial loading follow the current section, with separate profile and mod
  metadata readiness. Keep other sections available while editor data loads and
  show useful loading or failure feedback instead of an indefinite global loader.
- Recover stalled PWA updates with a bounded activation wait and an explicit retry
  action. Explain whether pending input, an operation, sign-in, or an open dialog
  is delaying an update; check input protection again before reloading. Other open
  windows retain their input and offer their own update action.
- Refine toast motion and preserve keyboard focus and reading position as
  notifications arrive or are dismissed. English and Russian remain supported.

### Reliability and extensions

- Unify panel process logging with timestamps, severity, source, and configurable
  `PZ_LOG_LEVEL`. Keep event-journal and notification delivery independent of the
  process-log threshold.
- Handle deeply nested damaged persisted data, malformed Steam responses and
  Workshop caches, and invalid Docker telemetry through their existing recovery
  or unavailable-data paths.
- Add explicit composition of trusted Python worker actions and monitoring
  channels. Extensions share the host's authentication, operation admission,
  localization, polling, and SSE delivery; built-in API contracts remain intact.
  See the [extension contracts and deployment example](https://github.com/Arnikes/pz-dashboard/blob/v1.9.0/docs/extensions.md).

### Upgrade notes

- MTProxy is optional; direct HTTPS Bot API delivery remains the default. Proxy
  delivery requires a Telegram application API ID and API hash in addition to
  the bot token. Paste the entire FakeTLS secret, including its encoded hostname,
  and enter a numeric Chat ID manually. An enabled proxy never falls back to a
  direct connection. Existing saved settings take precedence over environment
  bootstrap values. See [Telegram setup](https://github.com/Arnikes/pz-dashboard/blob/v1.9.0/docs/installation.md#telegram-and-mtproxy).
- Extensions run as trusted code inside the panel process and require an explicit
  deployment entrypoint. They provide backend capabilities without adding frontend
  controls or an automatic installation mechanism.
- After publication, use `ghcr.io/arnikes/pz-dashboard:v1.9.0` for the panel image,
  keeping its environment and persistent volumes. Pull and recreate only the
  `pz-dashboard` service; include both Compose files when using the existing-server
  overlay. Local builds and digest-pinned deployments must be updated from the
  host. See [released-image updates](https://github.com/Arnikes/pz-dashboard/blob/v1.9.0/docs/installation.md#released-images-from-ghcr)
  and [Maintenance self-update requirements](https://github.com/Arnikes/pz-dashboard/blob/v1.9.0/docs/installation.md#update-the-console-from-maintenance).
